モデル推論に使うアカウント、API キー、カスタムエンドポイント、ローカルモデルを管理する。設定サイドバーの「プロバイダー」を選ぶと、次の 4 つの子項目が開く。画面を開いた直後は先頭の「アカウント」が表示される。

| 子項目 | 主な内容 |
|---|---|
| [アカウント](#アカウント) | サブスクリプションや OAuth によるブラウザーサインイン |
| [API キー](#api-キー) | プロバイダーごとの API キーと Base URL |
| [カスタムエンドポイント](#カスタムエンドポイント) | OpenAI 互換などのエンドポイントを名前付きで保存・切り替え |
| [ローカルモデル](#ローカルモデル) | このマシン上でモデルをダウンロードして動かす |

表示中の子項目は URL パラメータ `pview` に保持されるため、各子項目へ直接リンクでき、再読み込みしても表示が維持される（既定の「アカウント」表示時はパラメータが省略される）。「ローカルモデル」は macOS / Windows / Linux（x64・arm64）では常に表示される。それ以外の環境では、アプリを `--local` フラグ付きで起動したときだけ表示される。

複数のプロファイルを持つ環境では、「アカウント」「API キー」「カスタムエンドポイント」の上部に「適用対象」チップが表示され、どのプロファイルの接続・キーを編集するかを選べる（プロファイルが 1 つだけなら表示されない）。OAuth の接続・切断、API キーの保存・削除、エンドポイントの保存はすべて選んだプロファイルに対して行われる。プロファイルを切り替えると、入力途中のキーと表示中の値は破棄される。

> [!important] 認証情報
> このページの値は秘密情報。Vault、スクリーンショット、Git、チャットへ実値を記録しない。

> [!note] シークレットマネージャからの供給（この画面に GUI なし）
> API キーは平文の `.env` に置く代わりに、`config.yaml` の `secrets.bitwarden` / `secrets.onepassword` 経由で外部シークレットマネージャ（Bitwarden Secrets Manager / 1Password）から起動時に取得する経路もある。いずれも既定は無効（`enabled: false`）で、この設定画面に対応する GUI 項目はなく、設定ファイルや `hermes secrets` サブコマンドから構成する。

> [!note] アカウントと API キーの生成元
> 「アカウント」と「API キー」は、統合プロバイダーカタログ（`hermes_cli/provider_catalog.py`）の `CANONICAL_PROVIDERS` から生成される。CLI の `hermes model` と同じ集合を共有するため、CLI で使えるプロバイダーは GUI のカードにも現れる。

> [!note] Gemini を使う経路
> Gemini は **Google AI Studio の API キー**（後述の API キーカード「Google AI Studio」、主キー `GOOGLE_API_KEY`）か、**Google Vertex AI プロバイダー**のどちらかで使う。Vertex AI（プロバイダー ID `vertex`、カタログの表示名は Google Vertex AI）は Gemini モデルを Vertex AI の OpenAI 互換エンドポイント経由で呼ぶ。GCP のサービスアカウント JSON または ADC（Application Default Credentials）から短命の OAuth2 トークンを自動発行・自動更新するため、静的な API キーが不要で、Vertex 特有のトークン失効に悩まされない。プロジェクトとリージョンは設定キー `vertex.project_id`（既定: 空）・`vertex.region`（既定: `global`）で指定する。**Vertex AI はデスクトップの「アカウント」一覧にカードとして表示されない**ため、利用は CLI（`hermes model`）や設定ファイルから行う。Gemini CLI の OAuth 経路（`google-gemini-cli` / `google-antigravity`）は廃止済みで、この画面には現れない。

> [!note] 使わないプロバイダーを隠す（この画面に GUI なし）
> `config.yaml` の `providers.<名前>.enabled: false` で、そのプロバイダーをモデルピッカー・`/models` 一覧・実行時解決・doctor 出力から隠せる（既定は有効）。`model_catalog.excluded_providers` にリストで指定したプロバイダーは、カタログから除外される。いずれも設定ファイル・CLI 経由の設定で、この画面に対応する GUI 項目はない。

## アカウント

サブスクリプションや OAuth を使ってブラウザーサインインする。API キーをコピーせずに接続できる。

このビルドの接続候補は10件。次はすべて未接続の状態で候補を展開したときの並びで、クライアント側のソート（`sortProviders` → `PROVIDER_DISPLAY` の order 値、次いで名前順）に従う。接続済みのアカウントは上部の「接続済み」グループへ浮上するため、実際の並びは接続状況で変わる。

| 画面表示（主） | プロバイダー ID（サブ） | 認証方式・用途 | 注意点 |
|---|---|---|---|
| Nous Portal | `nous` | oauth_device_code。Nous Portal へブラウザーサインイン | 「推奨」バッジ付きで先頭に表示される |
| モデルをローカルで実行 | ローカルモデルサブビューへ誘導する固定行 | 実機では接続候補の先頭に表示される（ソース上のスロットは Nous Portal 直下）。押下で「ローカルモデル」サブビューへ切り替え | キャッチコピーは「アカウント不要──モデルをダウンロードしてこのマシンで実行」。ローカルモデルが表示される環境（前述）だけに出る |
| OpenAI OAuth (ChatGPT) | `openai-codex` | ChatGPT アカウントの OAuth（device code） | API キー契約とは別の認証経路 |
| MiniMax | `minimax-oauth` | MiniMax アカウントの OAuth | 地域・契約により利用可能モデルが異なる |
| Qwen Code | `qwen-oauth` | Qwen CLI の認証フローを利用 | Qwen CLI 側の認証状態に依存 |
| xAI Grok | `xai-oauth` | xAI サブスクリプションの OAuth（loopback） | 対応サブスクリプションが必要。実機表示は短縮名「xAI Grok」 |
| Anthropic API Key | `anthropic` | 接続フロー内で Anthropic API キーを登録（Accounts タブでは PKCE フロー） | 使用量は Anthropic API 課金 |
| Anthropic OAuth: Required Extra Usage Credits to Use Subscription | `claude-code` | Claude Code 系の OAuth | 画面名どおり、サブスクリプション利用にも追加クレジットが必要 |
| GitHub Copilot (ACP) | `copilot-acp` | external_process。GitHub Copilot をエージェントとして認証 | `PROVIDER_DISPLAY` に order 値を持たないため、末尾（名前順）に並ぶ |
| Fireworks AI | `fireworks`（API キー側へ誘導する固定行） | 未接続候補を展開したときの末尾に OpenRouter と並ぶ固定行。押下で API キーサブビューへ切り替え | キャッチコピーは「直接モデル API — Fireworks がホストする最先端モデル」。展開時のみ表示 |
| OpenRouter | `openrouter`（API キー側へ誘導する固定行） | 未接続候補を展開したときの末尾の固定「OpenRouter」行。押下で API キーカタログへ遷移し `OPENROUTER_API_KEY` を設定 | API キーサブビューへの導線 |

`minimax-oauth` / `qwen-oauth` / `xai-oauth` は実機の表示名が `PROVIDER_DISPLAY` で短縮・改名されている（例: Qwen Code / xAI Grok）。Fireworks AI と OpenRouter の行は OAuth 接続候補ではなく、API キーサブビューへ切り替える固定行で、未接続候補を展開したときだけ「その他のプロバイダー」の末尾に並ぶ。[[03_設定/01_モデル|MoA プリセット]]は `moa` プロバイダーとしてカタログに載るが、認証が不要なためこの画面にカードは追加されない。

接続済みアカウントは上部へまとめて表示される。「別のプロバイダーを接続」から未接続候補を展開する。

### アカウント画面の全状態・操作

| 画面表示（主） | 内部状態・操作（サブ） | 製品初期状態 | 意味 |
|---|---|---|---|
| アカウントを接続 | 操作・保存キーなし | 該当なし | アカウントサブメニューの見出し |
| 接続済み | `status.logged_in: true` | `false`（通常は非表示） | バックエンドがログイン済みと判定したアカウント |
| その他のプロバイダー | UI 状態 `showAll: false → true` | `showAll: false` | 未接続候補を展開 |
| 別のプロバイダーを接続 | UI 状態 `showAll: false → true` | `showAll: false` | 接続済みアカウントがある状態で、追加候補を展開 |
| 折りたたむ | UI 状態 `showAll: true → false` | 非表示 | 未接続候補を閉じる |
| API キーをお持ちですか？ | サブビュー `keys` へ切り替え | 初期サブビューは `accounts` | 「API キー」サブメニューへ移動 |
| モデルをローカルで実行 | 固定行。サブビュー `local` へ切り替え | ローカルモデルが表示される環境のみ | ローカルモデルサブメニューへ移動 |
| Fireworks AI / OpenRouter | 固定行。サブビュー `keys` へ切り替え | 未接続候補の展開時のみ表示 | API キーサブメニューへ移動 |
| 切断 | 接続済み行の切断操作 | 非表示 | アプリ内の確認ダイアログ（確認ボタン「切断」）の後にログアウトする。切断に失敗した場合は失敗の通知が出る |
| 各プロバイダーカードの表示名 | 上表のプロバイダー ID | 未接続 | 共通オンボーディング画面でその ID の認証フローを開始 |

### CLI が管理するプロバイダー

GitHub Copilot (ACP) のように、外部の CLI が認証を管理するプロバイダーは、接続済みの行末にターミナルのアイコンが付く。行をクリックすると、ターミナルでそのプロバイダーの切断コマンドが実行される（詳細画面は開かない）。削除ボタンにはツールチップ「ターミナルで切断」が付く。行の下には「GitHub Copilot (ACP) is managed by its own CLI — remove it there.」のような英語の注記が出る（日本語リソース未整備のため英語表示）。

### Nous の無料枠

Nous Portal の無料枠（ゲスト）だけを使っている状態は「接続済み」として扱われず、Nous Portal は接続候補の先頭行に残る。製品既定の `nous.guest: true` では、ほかのプロバイダーが未設定のまま使い始めると、初回使用時に Nous の無料 ID が自動で作られる。本登録するには Nous Portal 行からサインインするか、`/login` を使う。`nous.guest: false` にすると無料枠を使わない。

## API キー

プロバイダーごとにカード化される。カード一覧の上部には検索ボックス（プレースホルダー「プロバイダーを検索…」）があり、カード名・環境変数名・説明文で絞り込める。主キーはカードの基本入力、その他はカード展開時の詳細項目である。

![設定 > プロバイダー > API キー 画面](@screenshots/settings-providers-apikeys.webp)

各行の右にはプレースホルダー「<名前> キーを貼り付け」の入力欄が、行頭には設定状態を示すドットが表示される。

- **共有キーのカード分割**: 1 つの環境変数を複数のプロバイダー構成が共有している場合（例: `DASHSCOPE_API_KEY`）、構成ごとに別のカードとして表示される。どのカードで入力しても同じキーに保存されるが、入力途中の下書きはカードごとに分かれる。
- **ディープリンク**: `?pview=keys&key=<環境変数名>` で開くと、検索の絞り込みが解除され、該当カードが展開された位置までスクロールする。
- 日本語入力の変換中に Enter を押しても保存されない。保存・削除の後はモデル候補が再取得される。

カード一覧のさらに上（検索ボックスより前）には、「**ローカル / カスタムエンドポイント**」の導線行がある。説明文は「OpenAI 互換のエンドポイント（Zyphra、vLLM、llama.cpp、Ollama など）を指定します。」で、押下するとオンボーディング画面のカスタムエンドポイントフォーム（URL と任意の API キー）が直接開く。環境変数ベースのカード一覧にはカスタムエンドポイントが載らないため、GUI からカスタムエンドポイントへ到達する入口としてこの行が置かれている。保存済みエンドポイントの一覧管理は後述の「カスタムエンドポイント」サブビューで行う。

### 詳細項目の意味

| 種類 | 意味 |
|---|---|
| `*_API_KEY`, `*_TOKEN` | API 認証用の秘密値 |
| `*_BASE_URL` | 標準 API 以外のプロキシ、地域別、ローカル、OpenAI 互換エンドポイント |
| `NVIDIA_BASE_URL` | build.nvidia.com またはローカル NIM の OpenAI 互換 URL |

### カードに表示されないプロバイダー変数

API キー画面は「既知のカード名」と「主キー」を持つグループだけを表示する。次は実行中バックエンドのカタログに存在するが、通常のカード一覧からは除外される。

| 変数 | 除外理由・用途 |
|---|---|
| `NOUS_BASE_URL` | Nous は OAuth で接続し、API キー側に主キー変数を持たないため |
| `HERMES_QWEN_BASE_URL` | Qwen OAuth ポータルの Base URL。主キー変数を持たず、Qwen Cloud カードの詳細にも表示されない |
| `AWS_REGION` | AWS Bedrock は API キーではなく AWS プロファイルと地域で認証するため |
| `AWS_PROFILE` | 同上（認証に使う AWS プロファイル名） |
| `BEDROCK_BASE_URL` | AWS Bedrock 用の Base URL。主キー変数を持たないため |

以前このリストにあった変数の現在の場所: `CLAUDE_CODE_OAUTH_TOKEN` は Anthropic カードの別名キー、`ALIBABA_CODING_PLAN_*` / `KILOCODE_API_KEY` / `NOVITA_*` はそれぞれ専用カードにある。逆に `HERMES_QWEN_BASE_URL` は Qwen Cloud カードの詳細欄ではなく、この非カード変数のリストにある。

これらはモデル設定フロー、CLI、設定ファイルなど別の経路で扱う。表示されない変数を無理に別カードへ入力しない。

上記のカードに表示されない変数も、製品既定値はすべて未設定。既存の外部 CLI、OS の資格情報ストア、環境変数から認証状態を検出した場合は、初回表示時点で接続済みになることがある。

## カスタムエンドポイント

第3のサブビュー。OpenAI 互換エンドポイント（vLLM、llama.cpp、Ollama、社内プロキシなど）を名前付きで複数保存し、テスト・有効化・削除で切り替えて使う。ナビのサブ項目名は「カスタムエンドポイント」と日本語化されているが、**画面本文（見出し・一覧・フォーム・ボタン・通知）は英語のみ**（日本語リソース未整備のため英語表示）。上部の「適用対象」チップで保存先のプロファイルを選べる。

API キーサブビュー先頭の「ローカル / カスタムエンドポイント」行が開くのは1件設定用のオンボーディングフォームで、こちらは保存済みリストの管理画面という関係にある。

### 保存済みエンドポイントの一覧

見出しは「Custom Endpoints」で、横に登録件数が表示される。各行の表示と操作:

| 画面表示（主） | 内部状態（サブ） | 意味 |
|---|---|---|
| 名前・Endpoint URL・モデル名 | `name` / `base_url` / `model` | 行本体。押すと下のフォームに読み込んで編集できる |
| Active バッジ | `is_current: true` | 現在使用中のエンドポイント |
| config.yaml バッジ | `source: 'direct-config'` | 設定ファイル直書き由来の項目。GUI から削除できない（削除ボタンが表示されない） |
| API キーのプレビュー | `has_api_key: true` | キー設定済みの場合にマスク済みプレビューを表示 |
| Use ボタン（「⚡ Use」） | 有効化（activate） | そのエンドポイントを使用中に切り替える。使用中の行では押せない |
| ゴミ箱アイコン | 削除（delete） | 「Delete <名前>?」の確認ダイアログの後に削除する |

1件も登録がない場合は「No custom endpoints」（Add an OpenAI-compatible endpoint below.）と表示される。

### 追加・編集フォーム

見出しは新規作成時「Add Endpoint」、既存項目の編集時「Edit Endpoint」。項目は次のとおり。

| 画面表示（主） | 内部フィールド（サブ） | 既定値 | 意味 |
|---|---|---|---|
| Name | `name` | 空 | 表示名（プレースホルダー例: Axet Proxy）。保存に必須 |
| Provider ID | `id` | 空 | プロバイダー ID（プレースホルダー例: axet-proxy）。空欄でも保存できる |
| Endpoint URL | `base_url` | 空 | ベース URL（プレースホルダー例: `http://127.0.0.1:8081/v1`）。保存に必須 |
| API Mode | `api_mode` | Auto-detect | 呼び出し方式。Auto-detect / Chat Completions / Responses API / Anthropic Messages から選ぶ。通常は Auto-detect のまま |
| Default Model | `model` | 空 | 既定モデル。入力欄に候補一覧が付くコンボボックスで、Test 実行後は発見済みモデルが候補に入る。保存に必須 |
| Context | `context_length` | 空（Auto） | コンテキスト長。空欄なら自動 |
| API Key | `api_key` | 空 | 任意。編集時に空欄のままなら既存キーを維持する（プレースホルダー「Leave blank to keep current key」） |
| Use for new chats | `make_default` | オン | 保存時にこのエンドポイントを新規チャットの既定にする |
| Discover models | `discover_models` | オン | モデル一覧の自動検出を有効にする |

既定値の列は新規作成時の初期状態（ソース由来）。実機では既存エンドポイントの編集状態（Edit Endpoint）で「Use for new chats」がオフ、「Discover models」がオンになっている例を確認しており、編集時は保存済みの値が読み込まれる。

ボタンは3つ（実機の表示は Test / Save / New endpoint）。

- **Test**: 到達確認（validate）。成功すると「Endpoint is reachable. Found N models.」と表示され、Default Model が未入力なら発見された先頭のモデルが自動入力される。実際にモデル一覧を返した URL が入力と違う場合（例: ルート URL を入れて `/v1` 側で応答した場合）は、Endpoint URL がその URL へ自動で補正される。Endpoint URL が空だと押せない。
- **Save**: 保存。Name・Endpoint URL・Default Model の3つが揃うまで押せない。成功すると「Custom endpoint saved.」と表示される。
- **New endpoint**: フォームを空にして新規作成に切り替える（既存項目の編集中だけ表示される）。

### 手順: ローカルの OpenAI 互換サーバーを登録する

前提: OpenAI 互換 API を公開するサーバーがローカルで起動している（例: vLLM や llama.cpp の `http://127.0.0.1:8000/v1`）。

1. 設定 → プロバイダー → カスタムエンドポイント を開く。
2. Name に表示名、Endpoint URL にベース URL（`/v1` まで含める）を入力する。
3. 「Test」を押す。期待結果: 「Endpoint is reachable. Found N models.」と表示され、Default Model に候補が入る。
4. 必要に応じて Context と API Key を設定し、「Save」を押す。期待結果: 「Custom endpoint saved.」と表示され、一覧に行が追加される。「Use for new chats」がオンのままなら、新規チャットの既定モデルがこのエンドポイントへ切り替わる。
5. 失敗時: 検証エラーが出る場合は、サーバーの起動状態、URL の `/v1` の付け忘れ、認証必須構成での API Key 未設定を順に確認する。切り分けの進め方は [[05_トラブルシューティング/01_問題の切り分け|問題の切り分け]] を参照。

## ローカルモデル

第4のサブビュー。アカウントも API キーも使わず、Hermes が管理する llama.cpp ランタイムでモデルをこのマシン上で動かす。macOS / Windows / Linux（x64・arm64）では起動フラグなしで常に表示され、サイドバーのサブ項目と、アカウント画面の接続候補の先頭に「モデルをローカルで実行 ─ アカウント不要──モデルをダウンロードしてこのマシンで実行」の行が現れる。それ以外の環境では、アプリを `--local` フラグ付きで起動したとき（`hermes desktop --local`）だけ表示される。画面の見出し・ボタン名はおおむね日本語化されている。

ローカルモデルの設定は常にアクティブなプロファイルに適用され、「適用対象」チップでは切り替えられない（画面に読み取り専用の注記が出る）。処理の途中で接続先やプロファイルが変わると、「ローカルモデルの接続が変更されました」というエラーが表示される。その場合は画面を開き直してから操作をやり直す。

![設定 > プロバイダー > ローカルモデル 画面](@screenshots/settings-providers-local.webp)

### クイックセットアップ

セットアップ前は、画面の先頭にクイックスタートの案内（hero）が出る。

- **推奨モデルがある場合**: このマシンの GPU メモリまたはユニファイドメモリに完全に収まる推奨モデルの名前と、ダウンロード容量を含む英語の説明（「One click sets everything up: …」）が表示される。「Set up for me」（英語表示）を押すと、ローカルエンジンのインストール、モデルのダウンロード、新しいチャットの既定モデルへの設定までをまとめて行う。「自分で選ぶ」を押すと、下の一覧から自分でモデルを選ぶ。
- **推奨モデルが無い場合**: hero は出ず、モデル一覧に「このマシン向けの自動推奨モデルはありません」という行と「モデルを探す」ボタンが表示される。自動セットアップには、GPU メモリまたはユニファイドメモリに完全に載ってフルスピードで動く厳選モデルが必要なため。一覧から選ぶか、Hugging Face から探す。
- ほかのダウンロードやインストールが進行中のとき、インストールに失敗したときも hero は表示されない。

hero の説明文と「Set up for me」は日本語リソース未整備のため英語表示。

### ダウンロードの進行表示

モデルのダウンロード中は、行に「ダウンロード中」の状態、進んだ量と全体量、転送速度、「残り約（時間）」が表示される。対応している場合は「一時停止」で止めて、「再開」で続きからダウンロードできる。一時停止中は「一時停止中」と表示される。完了すると「（モデル名） の準備ができました。」と通知される。

### 画面の構成

次の表は画面の上から順の構成。「このマシン」のバッジ値は環境依存。

| 画面表示（主） | 内容 |
|---|---|
| ローカルランタイム | 見出しの右にランタイムのビルド番号チップ。未インストール時は「ローカルランタイムをインストール」の説明（llama.cpp 推論エンジンで数百 MB をダウンロードする。ダウンロードしたモデルはすべてこのマシン上で動作し、アカウント不要でデータは外部に送られない）と「ランタイムをインストール」ボタンが出る。インストール後は状態表示（「準備完了 · <バックエンド>」「実行中」）と「オンにする」「オフにする」でローカルサーバーを起動・停止する（ソース確認）。オフにすると GPU メモリを全て解放し、再度オンにするまで新しいチャットはローカルモデルを使わない。新しいビルドがあると「エンジンの更新があります」と「エンジンを更新」が表示される |
| このマシン | GPU メモリ / RAM / ユニファイドメモリ の判定結果がバッジで並ぶ |
| モデル | カタログのモデル一覧（確認時の実機は Qwen3.8 27B / Qwen3.8 Flash Next / Qwen3.6 35B-A3B / DeepSeek V4 Flash の 4 件）。各行に説明文、適合バッジ（「このマシンには大きすぎます」「GPU に完全に収まります」「システム RAM を使用」）、「最大 256K コンテキスト」「画像対応」の能力バッジ、「ダウンロード · <サイズ> GB」ボタンが付く。ダウンロード後は「使用する」（新しいチャットがこのモデルを使う。「デフォルト」ピル）、「読み込み済み」とアンロード、配置表示（「すべて GPU 上」「一部 RAM 上」）、「おすすめ」判定（GPU に完全に載る最高品質 / 速度を保てる最良 / GPU 内で最速 / RAM 実行で最も快適 の 4 種の理由文）が加わる（ソース確認） |
| さらにモデルを探す | Hugging Face 全体を検索する欄（「モデル名または作者で検索」）。ここでダウンロードしたモデルは自動でマシンに合わせて動作するが、Hermes 側でのテストは行われていない旨の注記が付く。リポジトリ内ファイル一覧とゲート付きモデルの表示に対応する（ソース確認） |
| モデルファイルを追加 | 手持ちの GGUF ファイルを手動で追加する（サイドロード） |

関連する `config.yaml` キーは `local_runtime` セクション（`enabled` 既定 `false`、`backend` 既定 `auto`、`port` 既定 `0` で自動、`models_max` 既定 `4`）。実行中モデルはモデルピッカーの候補にも現れる。

## 操作

「API キー」サブビューのカード入力欄に共通する操作。

- **未設定の入力欄**: キーを入力すると「保存」が現れ、保存できる。
- **保存済みの入力欄**: 値はマスク表示される。フォーカスして新しい値を入力すると置き換えられる。
- **削除**: 編集状態で保存値を削除する。
- **Esc でキャンセル**: 入力中の変更を破棄し、保存済み状態へ戻す。
- **キーを取得**: カード展開時にプロバイダーの公式ページを開く。
- **カードを展開 / 折りたたむ**: Base URL などの詳細項目を表示・非表示にする。

この画面には保存済みキーの平文を表示する操作はない。マスク値から元のキーを復元できないため、必要な場合は発行元で再確認または再発行する。

## 推奨方針

1. サブスクリプション利用は「アカウント」を優先する。データを外部へ送りたくない、または費用をかけたくない場合は「ローカルモデル」を検討する。
2. API キーは用途別・端末別に発行し、利用上限を設定する。
3. Base URL はプロキシやローカルサーバーを使う場合だけ変更する。
4. 使わなくなった接続は Hermes とプロバイダー側の両方で失効させる。
